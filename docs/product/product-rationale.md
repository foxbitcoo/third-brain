# 从个人上下文到具体工作闭环

> 产品讨论整理。整理自最近两次产品讨论，不包含原始录音、身份、任职背景和内部业务数字。

## 问题如何收敛

最初希望做了解所有上下文的办公助理。实际探索发现：噪声来源可能更活跃，业务口径和承诺分散且可能冲突，全量重复处理的费用与收益不成比例。因此收敛到数据诊断DA和关键事项进展PMO；找人有价值，但缺少准确组织资料时不能猜测。

| 用户问题 | 所需上下文 | 应交付 | 不能冒充已完成 |
| --- | --- | --- | --- |
| 进展如何、卡在哪里 | 多群对话、计划、会议、周报和承诺变更 | 当前状态、跟进对象、冲突与待确认项，逐项有依据 | 自动催办、外部发送和组织承诺裁决 |
| 数据是多少、变化多少 | 对应看板、日期、指标、单位和比较口径 | 最短可核验结果与实际回执 | 用泛称或推送时间代替实际对象和统计日 |
| 为什么下降、继续查什么 | 总体和分群、分子分母、版本、入口、功能、发版和迁移事实 | 可证伪假设、获授权的下钻、解释与未解决项 | 把相关性当根因，或用正向分群代替总体结论 |
| 下次能否少解释一次 | 历史提问、交付、确认、人工修正和口径时效 | 有来源的Memory与实际注入记录 | 把“收到”当正确性证明，或永久复用历史数字 |

## 两次讨论带来的取舍

| 观点 | 产品影响 | 本轮采用方式 |
| --- | --- | --- |
| 简单问题不应强制写长报告 | 先判断交付目标，再决定深度 | Query分流独立，原模型继续写标准自然语言请求 |
| 简短提问隐含长期协作背景 | 引用对象与历史经验比单句文本更重要 | 保留原话、父消息、原图和统计日，复用适用口径 |
| 工单可以成为重复问题的经验载体 | 从展示历史走向可检查的复用 | 记录问题、报告、确认、Memory和实际注入，效果仍需验证 |
| 个人好用与通用产品成立不同 | 不用演示替代价值证据 | 当前定位个人原型，不宣称已证明商业化 |
| 技术复杂度本身不是亮点 | 用完整任务结果证明价值 | 看正确性、人工补充、时间与费用，不追求轮次和工具数量 |
| 规则与日期事实应分开沉淀 | 防止旧事实覆盖新事实 | 规范、口径和日期事实分别保留版本与适用条件 |

## 近期验收重点

1. 问数要对齐真实看板快照，分别保留统计日、推送日和引用原图，不能盲配最近一张。
2. 简单查数走短路径，缺必要字段时精确补充，不为跑满轮次制造问题。
3. 每轮回到原始问题，核对总体、单位、分子分母、时间和证据，不能仅凭高分放行。
4. 只复用获授权、已核验且适用的Memory，显示复用了什么及是否注入。
5. 用相同证据和截止时间做有/无Memory对照，记录人工补充、正确性、耗时和费用。
